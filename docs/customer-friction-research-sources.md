# 顧客の課題・摩擦を発見するための情報源

## 目的

ビジネスアイデアを考える際に、単に「面白そうなアイデア」を探すのではなく、  
**顧客が実際に感じている課題・不満・不便・不安・回避行動を、複数の情報源から確認する**ことを目的とする。

課題探索では、特に次の流れを意識する。

```text
顧客の声
  ↓
既存サービスの不足
  ↓
現在の回避策
  ↓
支払意思
  ↓
需要・市場規模
  ↓
解決策の仮説
```

---

## 情報の種類とおすすめ情報源

| 情報の種類 | 確認したいこと | 主な情報源 | 見るポイント |
|---|---|---|---|
| **生の不満・悩み** | 人が実際に何に困っているか | Reddit / Yahoo!知恵袋 / Hacker News | 「困る」「面倒」「できない」「どうしている？」などの具体的な発言 |
| **既存製品への不満** | 現在の解決策では何が足りないか | App Store / Google Play / G2 / Capterra / GitHub Issues | 低評価レビュー、Feature Request、回避策、他ツール併用 |
| **現在の回避策** | 顧客が問題をどう無理やり解決しているか | Reddit / GitHub Issues / レビューサイト / SNS | Excel、手作業、コピペ、自作スクリプト、複数サービス併用 |
| **支払意思** | 解決のために実際にお金を払う課題か | Lancers / CrowdWorks / 外注募集 | 発注内容、予算、繰り返し依頼されている仕事 |
| **需要の変化** | その課題への関心が増えているか | Google Trends | 検索量の推移、急上昇ワード、関連検索 |
| **課題の深刻度** | どれほど強い困りごとか | PIO-NET / 消費生活相談 / Reddit等 | 相談件数、繰り返し発生、金銭的・時間的損失 |
| **市場規模・対象人数** | その課題を持つ人・企業がどれくらいいるか | e-Stat / 業界統計 / 各省庁統計 | 人口、企業数、施設数、業界規模 |
| **新しい解決策・競合** | どのようなサービスが既に存在するか | Product Hunt / App Store / G2 / Capterra | 新規サービス、競合の強み、未解決の不満 |

---

## 各情報源の使い方

### 1. Reddit

**用途：生の課題・不満を探す**

おすすめ検索例：

```text
○○ frustrating
○○ annoying
alternative to ○○
wish there was
how do you manage ○○
manual workflow
takes too long
```

特に重要なのは、「○○が欲しい」という要望よりも、

- 毎回手作業で処理している
- Excelで代用している
- 複数サービスを使い分けている
- 自分でスクリプトを書いている

といった**現在の回避策（workaround）**。

---

### 2. App Store / Google Play

**用途：既存アプリの未解決課題を探す**

特に★1〜3のレビューを見る。

注目する表現：

```text
○○できない
毎回○○する必要がある
○○機能が欲しい
高すぎる
別アプリを併用している
アップデート後に使いにくくなった
```

特に、

```text
サービスA
+
サービスB
+
手作業
```

のように複数の方法を組み合わせている場合、  
1つのサービスでまとめて解決できる可能性がある。

---

### 3. G2 / Capterra

**用途：B2B SaaS・業務システムの課題探索**

確認する項目：

- What do you dislike?
- Cons
- Feature Request
- 利用企業規模
- 業界
- 現在解決している業務

重要な状態：

```text
需要がある
+
市場が既に存在する
+
現在の商品でも不満が残っている
```

これは新しいサービスを考える上で強いシグナルになる。

---

### 4. GitHub Issues

**用途：開発者・技術者向けサービスの課題探索**

検索例：

```text
label:enhancement
feature request
manual
workflow
workaround
annoying
slow
difficult
```

特に、

> 「現在はこのスクリプトで回避している」

というIssueは重要。

ユーザー自身が解決策を作っているため、  
**課題の強さを示す証拠**になりやすい。

---

### 5. Lancers / CrowdWorks

**用途：お金を払って解決しようとしている課題を探す**

レビューサイトとの違い：

```text
レビュー
→ 「困っている」

クラウドソーシング
→ 「困っているので、お金を払って解決してほしい」
```

注目する案件：

- Excel自動化
- データ収集
- データ入力
- RPA
- AI自動化
- リサーチ
- 営業支援
- Webスクレイピング
- 定型業務の自動化

同種の依頼が繰り返されている場合、

```text
手作業
↓
外注
↓
ツール化
↓
SaaS化
```

できる可能性がある。

---

### 6. Google Trends

**用途：見つけた課題の需要を検証する**

確認すること：

- 検索需要は増えているか
- 季節性はあるか
- 地域差はあるか
- 関連検索は何か
- 急上昇しているキーワードは何か

Google Trendsだけで課題を発見するのではなく、

```text
Redditなどで課題発見
        ↓
Google Trendsで需要確認
```

という使い方が有効。

---

### 7. PIO-NET / 消費生活相談

**用途：日本国内の強い消費者課題を探す**

対象例：

- 通販
- サブスクリプション
- 金融
- 通信
- 中古品
- 引越し
- ペット
- 契約トラブル

相談窓口まで問い合わせるほどの問題なので、  
SNS上の不満よりも**深刻度の高い課題**を見つけられる可能性がある。

---

### 8. Hacker News

**用途：エンジニア・スタートアップ領域の課題探索**

検索例：

```text
Ask HN: How do you...
Ask HN: What do you use for...
Ask HN: What's your biggest problem with...
Ask HN: alternative to...
```

特に、

- 開発者ツール
- SaaS
- 自動化
- AI
- 生産性
- インフラ
- 開発ワークフロー

などの課題探索に向いている。

---

### 9. Product Hunt

**用途：新しい解決策・競合サービスを探す**

見るポイント：

- 最近登場したサービス
- コメント
- レビュー
- 「なぜこのサービスを作ったか」
- 既存サービスとの違い
- ユーザーからの改善要望

課題発見そのものより、

```text
この課題に対して
どんな解決策が既に試されているか
```

を見るために使う。

---

### 10. Google Maps

**用途：店舗・地域サービスの課題探索**

向いている業界：

- 飲食
- ホテル
- 美容
- 医療
- スクール
- ペット
- 修理
- 不動産

低評価レビューから、

```text
予約しづらい
待ち時間が長い
説明が分かりにくい
料金体系が分かりづらい
駐車場が分かりにくい
問い合わせが面倒
```

など、現場に近い課題を発見できる。

---

### 11. Yahoo!知恵袋

**用途：日本人の生活上の悩みを探す**

検索例：

```text
○○ 困っています
○○ 面倒
○○ できません
○○ どうしていますか
○○ おすすめありますか
```

「おすすめありますか？」という質問も重要。

現在の選択肢では満足できていない可能性があるため、  
**既存サービスの不足**を見つけられる。

---

### 12. e-Stat

**用途：課題を持つ人・企業の母数を確認する**

例：

```text
介護施設の業務課題を発見
        ↓
全国の介護施設数を調査
        ↓
対象市場の母数を推定
```

課題発見というより、

**発見した課題の市場規模を確認するための情報源**

として使う。

---

## おすすめの調査フロー

基本的には、次の順番で調べる。

```text
① 生の声
Reddit / 知恵袋 / Hacker News
        ↓
② 既存サービスの不満
App Store / Google Play / G2 / Capterra / GitHub Issues
        ↓
③ 現在の回避策
Excel / 手作業 / コピペ / 自作ツール / 複数サービス併用
        ↓
④ 支払意思
Lancers / CrowdWorks
        ↓
⑤ 需要確認
Google Trends
        ↓
⑥ 市場規模
e-Stat / 業界統計
        ↓
⑦ 解決策の仮説
```

---

## 摩擦を記録するときの項目

課題を見つけたら、単なる「アイデア」としてではなく、  
**課題の証拠**として保存する。

| 項目 | 内容 |
|---|---|
| Customer | 誰が困っているか |
| Situation | どんな状況で起きるか |
| Job | 何をしようとしているか |
| Friction | 何が邪魔になっているか |
| Current workaround | 現在どう対処しているか |
| Frequency | どのくらい頻繁に発生するか |
| Severity | どれほど困っているか |
| Payment evidence | 解決のためにお金を払っているか |
| Existing solution | 現在使われている商品・サービス |
| Source | 情報源 |
| Evidence | URL・発言・レビュー |
| Hypothesis | 考えられる解決策 |

## 重要な考え方

### 「要望」より「行動」を見る

```text
「こんなアプリが欲しい」
```

よりも、

```text
毎週Excelで3時間かけて処理している
```

の方が強い情報。

顧客が実際に時間・労力・お金を使っているからである。

---

### 「不満」だけでなく「回避策」を探す

特に重要なシグナル：

```text
Excelで管理
手作業
コピペ
自作スクリプト
複数サービス併用
人に外注
```

これは、

> 問題があるだけでなく、ユーザーがすでに解決しようとしている

ことを意味する。

---

### 1つの情報源だけで判断しない

理想的には、

```text
Reddit
「困っている人がいる」

        +

レビュー
「既存商品にも不満がある」

        +

CrowdWorks
「実際にお金を払っている」

        +

Google Trends
「需要が存在・成長している」

        +

e-Stat
「対象となる人・企業が十分いる」
```

というように、複数の情報を組み合わせる。

---

## まとめ

顧客課題を探すときの中心は、

```text
不満
↓
回避策
↓
支払意思
↓
需要
↓
市場規模
```

で考える。

特に最初に使いやすい組み合わせは、

```text
Reddit / 知恵袋
        ↓
App Store / G2 / GitHub Issues
        ↓
Lancers / CrowdWorks
        ↓
Google Trends
        ↓
e-Stat
```

である。

ビジネスアイデアを考えるときは、

> 「何を作るか」

から始めるのではなく、

> **「誰が、どんな状況で、何に困り、今どう対処しているのか」**

を観察することから始める。
